# Before You Start

Before opening an issue or writing code, please:

1. Read the README.
2. Search existing Issues.
3. Search open Pull Requests.
4. Discuss large changes before implementing them.

Large architectural changes should always be discussed first to avoid duplicate work.

# Branching Strategy

Never commit directly to the main branch.

Create a feature branch.

```
feature/add-user-authentication
```

Bug fixes

```
fix/login-validation
```

Documentation

```
docs/update-api-reference
```

Refactoring

```
refactor/database-layer
```

---

# Coding Standards

Please follow these principles:

- Write readable code.
- Keep functions small.
- Avoid unnecessary complexity.
- Prefer meaningful variable names.
- Document public APIs.
- Remove dead code.
- Avoid commented-out code.
- Keep commits focused on one change.

If formatting tools are configured, run them before committing.

---

# Commit Message Guidelines

Follow the Conventional Commits specification.

Examples

```
feat: add deployment pipeline

fix: resolve authentication bug

docs: update installation guide

refactor: simplify cache manager

test: add unit tests for parser

chore: update dependencies
```

Avoid commit messages like

```
update

changes

fix

done

asdf
```

# Pull Request Process

Before opening a Pull Request, ensure that:

- Your branch is up to date.
- The project builds successfully.
- Tests pass.
- Documentation has been updated if necessary.
- New functionality includes appropriate tests.

Pull Requests should include:

- A clear title.
- A description of the change.
- Motivation for the change.
- Screenshots (if UI changes).
- Linked issue (if applicable).

---

# Reporting Bugs

Before submitting a bug report:

- Verify the issue still exists.
- Search existing Issues.

A good bug report includes:

- Expected behavior
- Actual behavior
- Steps to reproduce
- Screenshots (if applicable)
- Environment information

Example

```
Operating System:
Browser:
Project Version:

Steps to reproduce:

Expected Result:

Actual Result:
```

# Suggesting Features

Feature requests should clearly explain:

- The problem being solved.
- The proposed solution.
- Possible alternatives.
- Additional context.

Good feature requests focus on user value rather than implementation details.

# Review Process

Every Pull Request will be reviewed by one or more maintainers.

During review you may be asked to:

- Make code changes
- Improve documentation
- Add tests
- Simplify implementation
- Rebase your branch

Constructive discussion is encouraged throughout the review process.
